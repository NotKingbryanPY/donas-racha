# Corte definitivo a Supabase

La web opera con Supabase mediante las funciones `/api/*` de Vercel. Vercel valida las sesiones y guarda la clave de servicio en el servidor; el navegador nunca recibe esa clave. Clientes entran con su ID y contraseña opcional; vendedores/administradores entran con el correo y contraseña de Supabase. Las altas, compras liquidadas, puntos, rachas, insignias, canjes, pedidos, estadísticas y configuración se leen o escriben en Supabase. El código de Apps Script queda solo como fuente histórica para una exportación final.

## Antes de publicar

1. Respaldar el proyecto Supabase y las hojas. Aplicar `supabase/migrations/202609250003_supabase_loyalty_cutover.sql` en un proyecto de prueba primero y luego en producción. La migración crea las funciones transaccionales y los ajustes; no importa clientes ni modifica Apps Script.
2. Identificar el proyecto Apps Script de la **URL `/exec` que se usa realmente** y leer su propiedad `SPREADSHEET_ID`. No elegir una hoja solo por su nombre: en la revisión del 26 de septiembre, la implementación activa apuntaba a una hoja titulada «Respaldo antes de fase 1», mientras la hoja titulada simplemente «Donas Racha» estaba desactualizada. Detener nuevas escrituras en la hoja activa (altas, compras y canjes) durante el corte y mantener la web antigua sin publicitar nuevos pedidos. Exportar inmediatamente con `exportPhase5MigrationData()` desde ese proyecto y descargar el JSON privado. La exportación del 22 de septiembre no sirve: contenía 21 clientes y la hoja activa ya contenía 40 el 26 de septiembre. La exportación final debe tener menos de 24 horas.
   Si el exportador de Apps Script pide permisos adicionales, también se puede descargar la hoja activa como XLSX y convertirla localmente con `python scripts/phase17-xlsx-export.py --input "C:\ruta\hoja-activa.xlsx" --output "C:\ruta\privada\export-reciente.json" --spreadsheet-id "ID_DE_LA_HOJA_ACTIVA"`. Requiere `openpyxl`; las fechas se interpretan en `America/Bogota`. Confirmar que el libro descargado contiene las siete pestañas de datos y comparar algunas fechas con una exportación anterior. No importar la hoja antigua.
3. En esta carpeta ejecutar:

   ```powershell
   node scripts/phase17-cutover.mjs --input "C:\ruta\al\export-reciente.json" --report "C:\ruta\privada\cutover-report.json" --sql-out "C:\ruta\privada\cutover.sql"
   ```

   Revisar `blockingErrors = 0`, cantidad de clientes, transacciones, canjes y fecha del export. No colocar el JSON, reporte ni SQL generado en Git; contienen datos personales.
4. Ejecutar el SQL generado en el SQL Editor del proyecto Supabase correcto, **completo y sin seleccionar solo un fragmento**. Desde el 26 de septiembre el generador emite una sola sentencia `DO` para que las tablas temporales y las comprobaciones se ejecuten en la misma transacción; no reutilizar un SQL anterior de varias sentencias que falle con `cutover_customers does not exist`. Si el editor advierte sobre tablas creadas sin RLS, se refiere a las tablas temporales del corte: elegir «Run without RLS». Las tablas permanentes ya tienen sus políticas en las migraciones; no aplicar «Run and enable RLS» al importador. Si detecta IDs que pertenecen a otra cuenta, actividad de puntos nueva en Supabase/Android o pedidos liquidados después del export, se revierte entera. **No eliminar esos guardas**. Conciliar esa actividad y crear otro export antes de reintentar. El script conserva pedidos, vínculos de sesión y contraseñas opcionales; reemplaza solo los datos heredados de Sheets para los clientes del export.
5. Comprobar en Supabase que el ID registrado el día del fallo está en `public.customers` con `status = 'ACTIVE'`, que tiene fila en `loyalty_accounts` y `customer_streaks`, y que saldos, compras y canjes coinciden con la última hoja. Comprobar otros clientes representativos y el total de clientes. El panel mostrará migración completada después del SQL.
6. Desplegar la rama web después de la comprobación. Probar alta de un cliente de prueba, ingreso por ID, perfil, compra liquidada por vendedor, canje, pedido, pago presencial y finalización. Una orden pendiente no acredita puntos; la finalización pagada sí, como máximo una vez por día. Verificar el correo administrador ya configurado en Supabase; la antigua contraseña compartida de Sheets deja de autenticar.
7. Reemitir los QR ya compartidos antes de retirar Apps Script. El importador conserva el ID del cliente, pero **no importa `Clientes.QR_URL`**: la web nueva genera un QR que apunta a su perfil en Vercel. Una tarjeta o imagen antigua aún codifica el enlace a Apps Script; el lector QR de la web nueva puede extraerle el ID, pero la cámara normal del teléfono abrirá el enlace viejo. Enviar o imprimir el QR nuevo para cada cliente que dependa del anterior. Las imágenes de QR se generan mediante `api.qrserver.com`; Supabase guarda el ID y los datos del cliente, no el PNG.
8. Restringir o retirar la implementación web antigua de Apps Script una vez reemplazados los QR antiguos. Hasta entonces, aunque la nueva web ya no la llama, la URL antigua sigue respondiendo y puede divulgar IDs y perfiles. Conservar el JSON y respaldo de Sheets fuera del repositorio para auditoría y recuperación.

El exportador de fase 5 no incluye la hoja `Config`. Se consultaron los valores públicos actuales de `getConfig`: modo diario, tolerancia 3 días, precio B/.1.00 y puntos 10/12/15/17; son los valores iniciales de `business_settings`. Antes de publicar, confirmar que no cambiaron durante el corte y ajustar la configuración desde el panel Supabase si hace falta. `COMPRAS_RECOMPENSA=5` es una clave heredada: el código actual de compras no la usa para entregar premios automáticos; los canjes por puntos permanecen disponibles.

La revisión del 26 de septiembre confirmó que producción tenía 21 clientes y dos pedidos sin completar antes del corte. La conversión de la hoja activa preparó 40 clientes, 19 transacciones, cinco recompensas y seis definiciones de insignias sin errores bloqueantes; no había canjes en la exportación. Hubo dos teléfonos inválidos, una insignia huérfana y avisos de puntos por compras que superaban el total histórico. Los clientes con teléfono inválido podrán consultar su perfil, pero deberán corregir su WhatsApp antes de pedir delivery.

**Corte ejecutado el 26 de septiembre de 2026:** `business_settings.legacy_imported_at` quedó en `2026-09-26 17:08:14 UTC`. En Supabase se verificaron 40 clientes activos, 40 accesos web, 40 cuentas de puntos, 40 rachas, 19 transacciones de fidelidad, 77 alias, 17 insignias asignadas y cinco recompensas. Los saldos suman 190 puntos y 19 compras; no hay accesos, cuentas ni rachas faltantes. La hoja activa indicaba una última modificación anterior al corte. En el despliegue de prueba de Vercel se comprobó el catálogo, ranking y acceso por ID a un perfil importado, incluido el formulario de pedido dentro del perfil. No se efectuó un pedido ni un cobro de prueba sobre datos productivos. La importación ya se completó: **no ejecutar de nuevo un SQL antiguo** que use `cutover_customers`. Un error posterior sobre esa tabla temporal no implica que se haya revertido la importación anterior.

Las pruebas locales cubren `tests/phase17-postgres.sql` en PostgreSQL 18 desechable y `tests/phase17-cutover.cjs`. Quedan pendientes una prueba real de vendedor, compra, canje y pedido pagado, además de reemitir los QR antiguos. No retirar Apps Script mientras se sigan usando esos QR.
